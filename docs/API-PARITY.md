# API parity across Python, C++, Rust and C

Generated by `tools/api_inventory.py` from `tools/api_parity.toml`; do not edit by hand.
`python/tests/test_api_parity.py` fails when a listed name is missing from a surface
or when this file is stale. One operation, one name; a dash marks an operation a
surface does not offer, with the reason.

Python names are `Class.method`; properties are listed like methods. C++ and Rust names
are `Type::method`. C names are the exported symbols; the `_ex`, `_opt` and `_named`
suffixes are the ABI's additive variants and are documented in the header.

## Conventions

- Python exposes constant facts as properties (`robot.component_names`); C++ and Rust use methods of the same name.
- Rust methods return `Result`; C++ throws `dexcontrol::Error`; Python raises typed exceptions; C returns `dex_status_t` with a `dex_error_t`.
- Freshness bounds are `max_age` seconds in Python, `std::chrono::milliseconds` in C++, `Option<Duration>` or `DurationLimit` in Rust, and `max_age_ms` on the C `_ex` variants.
- Where C++ or Rust return JSON text (`*_json`), Python returns the parsed dictionary under the name without the suffix.
- Per-joint step limits use `command_position` in C++ and Rust; Python spells the same call `set_joint_pos(q, max_steps=...)`.
- Python sensor accessors return handles (`sensors.get_imu(name).get_obs()`); the C++ and Rust `Sensors` view returns the latest sample (`sensors().imu(name)`), with the same freshness arguments.
